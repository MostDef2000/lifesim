# Контракт design issue для ВЛ1

Статус: Active  
Проект: **ВЛ1: Рейнеке**

Этот документ задаёт формат задач на визуальный дизайн. Его цель — превращать идеи, референсы и визуальные исследования в bounded design issues, которые затем можно передать в отдельную техническую реализацию.

## Основные правила

1. Один design issue = один конкретный дизайн-объект или один конкретный пользовательский сценарий.
2. Design issue описывает **что должен видеть и понимать игрок**, а не способ реализации.
3. В design issue не должно быть кода, псевдокода, SQL, схем API или указаний по внутренней архитектуре.
4. Техническая реализация оформляется отдельно.
5. Если дизайн противоречит канону проекта или текущему `docs/SPEC-V0.1.md`, конфликт должен быть явно вынесен на решение владельца проекта.
6. Реализация не должна молча менять игровой канон ради удобства UI.
7. Визуальные референсы задают направление, но не являются указанием копировать конкретный чужой продукт.
8. Если для задачи нужен новый визуальный канон, его сначала следует утвердить, а затем использовать в последующих design issues.

---

## 1. Что проектируем

Указать один конкретный объект.

Примеры:

- основной экран мира;
- карточка NPC;
- режим разговора;
- экран создания персонажа;
- экран события;
- причал;
- общий дом;
- магазин;
- интерьер комнаты;
- одежда конкретной социальной роли;
- визуальный стиль одной категории объектов.

Не использовать формулировки уровня «сделать UI игры», «проработать контент» или «сделать мир красивее».

---

## 2. Игрок видит / делает

Описать 2–6 конкретных пунктов:

- что игрок видит при входе в этот экран или сцену;
- на что должен обратить внимание в первую очередь;
- какие действия ему доступны;
- что меняется после действия;
- какая информация основная;
- какая информация второстепенная;
- какой результат действия получает игрок.

Формулировки должны описывать игровой опыт, а не внутреннюю реализацию.

---

## 3. Визуальная задача

Кратко описать требуемое впечатление и визуальную иерархию.

Нужно зафиксировать:

- настроение;
- степень реализма;
- плотность информации;
- уровень «игрового UI» против ощущения живого мира;
- ключевые ассоциации;
- элементы, которых следует избегать.

Пример:

> Интерфейс должен восприниматься как окно в живой островной мир, а не как административная таблица. Основное внимание — персонажу и месту; числовые параметры вторичны.

---

## 4. Обязательные элементы

Перечислить всё, что должно присутствовать в утверждённом варианте.

Для UI это могут быть:

- персонаж;
- текущая локация;
- время;
- погода;
- текущая задача;
- потребности;
- основные действия;
- переход к диалогу;
- визуальная сцена.

Для world/character design:

- материалы;
- форма;
- одежда;
- характерные предметы;
- окружение;
- освещение;
- масштаб;
- признаки социальной роли.

---

## 5. Визуальные референсы

Приложить или перечислить подходящие референсы:

- изображения;
- фотографии;
- фильмы;
- игры;
- архитектуру;
- реальные места;
- UI-примеры;
- художественные направления.

Для каждого важного референса желательно кратко указать, **что именно** из него используется как ориентир: композиция, атмосфера, материалы, освещение, плотность UI и т. п.

Референс не является указанием копировать конкретные ассеты, персонажей или фирменный интерфейс.

---

## 6. Артефакты дизайна

Указать, что должно быть подготовлено до передачи в реализацию.

Типовой набор:

- 2–4 визуальных направления или варианта;
- выбранный вариант;
- финальный mockup / style frame / concept frame;
- описание поведения интерактивных элементов;
- список необходимых состояний;
- при необходимости — prompt/reference для Flux;
- при необходимости — перечень канонических визуальных решений, которые должны быть переиспользованы дальше.

Для простой задачи достаточно одного итогового артефакта, если альтернативы не нужны.

---

## 7. Состояния

Для интерфейса перечислить применимые состояния.

Например:

- normal;
- selected;
- active;
- loading;
- empty;
- error;
- disabled;
- unavailable;
- completed.

Для world/character design вместо UI-состояний могут использоваться контекстные состояния:

- день / ночь;
- хорошая / плохая погода;
- рабочее / бытовое состояние;
- новое / изношенное;
- спокойная / аварийная сцена.

Не добавлять состояния, которые не нужны конкретной задаче.

---

## 8. Критерий приёмки дизайна

Дизайн считается готовым к технической реализации, когда:

- понятна визуальная иерархия;
- понятно, что видит и делает игрок;
- все обязательные элементы присутствуют;
- определены необходимые состояния;
- выбран один канонический вариант;
- существует конкретный визуальный артефакт или однозначное описание, от которого можно реализовывать результат;
- нет неразрешённых противоречий с каноном проекта.

Если задача предполагает UI, критерий должен позволять визуально сравнить реализацию с утверждённым mockup.

---

## 9. Не трогаем

Явно перечислить границы задачи.

Примеры:

- не менять simulation logic;
- не менять экономику;
- не добавлять новые игровые механики;
- не менять API;
- не проектировать мобильную версию;
- не менять другие экраны;
- не пересматривать канон персонажей;
- не менять баланс.

Если для реализации дизайна позже потребуется расширить эти границы, это оформляется отдельной задачей.

---

## 10. Зависимости

Указать только реальные зависимости.

Примеры:

- утверждённый визуальный стиль мира;
- готовый экран мира;
- существующая механика диалога;
- canonical portrait персонажа;
- конкретная игровая система;
- другой design issue.

Если зависимостей нет, написать: **нет**.

---

## 11. Метка

У design issue должна быть одна основная дизайн-метка:

- `design-ui` — интерфейсы, экраны, UX и информационная иерархия;
- `design-world` — локации, архитектура, природа и окружение;
- `design-character` — персонажи, одежда, внешний вид и социальные роли;
- `design-visual` — общая визуальная система, стиль генерации, композиция, визуальные правила.

Не использовать несколько основных design-меток для одной задачи. Если задача охватывает несколько областей, её следует разделить.

---

## Передача в реализацию

После утверждения design issue его результат становится входом для отдельной implementation-задачи.

Рекомендуемая цепочка:

**идея → визуальное исследование → варианты → выбранный канон → design issue закрыт → implementation issue → bounded PR → тест → игровой smoke-test**

Design issue не должен превращаться в implementation backlog внутри одного issue.
