# ВЛ1: Рейнеке

## 1. Общая концепция

**ВЛ1** — браузерный многопользовательский симулятор жизни с автономным ИИ-миром.

Первый игровой мир разворачивается на **острове Рейнеке рядом с Владивостоком**.

В момент запуска используется реальная география как исходная точка, однако после старта сервер начинает жить собственной историей.

Игровой мир постепенно расходится с реальностью:

* появляются новые здания;
* старые здания могут исчезать;
* меняется инфраструктура;
* возникают организации;
* меняются правила общины;
* происходят социальные конфликты;
* формируются семьи;
* появляются новые жители;
* жители стареют и умирают;
* меняются экономика и распределение собственности.

Реальный остров используется только как географическая основа.

Все жители, биографии и происходящие внутри игры события являются вымышленными.

---

# 2. Основная идея

Игрок получает не обычного игрового персонажа, а **автономного цифрового человека**.

Персонаж способен жить самостоятельно:

* есть;
* спать;
* работать;
* зарабатывать;
* покупать вещи;
* общаться;
* заводить отношения;
* конфликтовать;
* посещать другие места;
* принимать решения;
* выполнять обязанности;
* реагировать на события;
* строить планы.

Когда игрок не вмешивается, персонаж продолжает существовать самостоятельно.

Игрок может в любой момент:

1. наблюдать;
2. задавать персонажу цели;
3. давать конкретные поручения;
4. изменять приоритеты;
5. вмешиваться в отдельные действия;
6. полностью перехватывать управление.

Таким образом персонаж одновременно является:

**автономным агентом + игровым аватаром пользователя.**

# 3. Философия игры

ВЛ1 должен быть пространством ролевого эксперимента.

Игрок может попробовать социальные роли и образ жизни, которых у него никогда не будет в реальности.

Например:

* рабочий;
* предприниматель;
* врач;
* полицейский;
* фермер;
* художник;
* политический лидер общины;
* безработный;
* преступник;
* затворник;
* общественный активист;
* владелец бизнеса;
* член коммуны.

Игровой мир не должен заранее определять «правильный» способ жизни.

Однако свобода действий существует внутри причинно-следственной модели мира.

Если персонаж нарушает игровые законы, это вызывает соответствующие последствия.

# 4. Первый игровой сервер

Рабочее название:

**ВЛ1: Рейнеке**

Первоначальный масштаб:

* несколько десятков NPC;
* небольшая автономная община;
* несколько реальных игроков;
* остров как детализированная игровая территория;
* Владивосток как внешний условно симулируемый город.

Первоначальная община представляет собой экспериментальное поселение совершеннолетних персонажей с элементами:

* контркультуры;
* культуры коммун 1960-х;
* натуризма;
* технологического утопизма;
* условного технокульта.

Это исключительно вымышленная культура игрового мира.

---

# 5. Возрастной рейтинг

Проект является **строго 18+**.

Все персонажи, участвующие в романтических или сексуальных сценариях, должны быть однозначно совершеннолетними.

Базовые ограничения мира:

* отсутствие сексуального контента с несовершеннолетними;
* отсутствие сексуального насилия;
* отсутствие использования реальных людей как сексуальных прототипов;
* отсутствие генерации персонажей, намеренно копирующих конкретного реального человека.

Взаимодействия между персонажами могут включать взрослые добровольные отношения.

Между реальными игроками механика должна учитывать согласие участников.

Мир допускает насильственные и преступные действия как часть ролевой симуляции.

Например:

* драка;
* нападение;
* кража;
* ограбление;
* уничтожение имущества;
* убийство;
* незаконная деятельность.

Такие действия не существуют отдельно от социальной системы.

Они могут приводить к:

* свидетелям;
* вызову полиции;
* расследованию;
* задержанию;
* суду;
* штрафам;
* заключению;
* травмам;
* смерти;
* изменению общественной репутации;
* мести;
* конфликтам;
* изменению отношений;
* экономическим последствиям.

Основной принцип:

**действие → состояние мира → реакция окружающих → последствия.**

## Владивосток

На первом этапе Владивосток не требует полной симуляции.

Он существует как внешний мир.

Персонаж может иметь там:

Пример:

`Рейнеке → поездка → Владивосток → выполнение задачи → возвращение`

Позже Владивосток может постепенно становиться полноценной игровой территорией.

# 10. Социальная модель

Отношение между двумя персонажами не должно храниться одним числом.

Пример:

```text
отношения:
доверие: 72
симпатия: 55
уважение: 81
страх: 4
романтический интерес: 23
сексуальный интерес: 10
раздражение: 8
```

Дополнительно существует история событий:

```text
Иван помог Анне при пожаре.
Анна дала Ивану деньги.
Иван солгал Анне.
Они вместе работали 14 дней.
```

LLM получает эту информацию при взаимодействии персонажей.

# 11. Память NPC

Память делится на несколько уровней.

### Краткосрочная память

Последние события и текущий разговор.

### Эпизодическая память

Важные личные события:

* конфликт;
* знакомство;
* свадьба;
* увольнение;
* травма;
* преступление;
* смерть знакомого.

### Семантическая память

Устойчивые знания:

* кто кем является;
* где находится объект;
* правила общины;
* отношения между людьми.

### Биография

Сжатая история жизни NPC.

Полная история не должна постоянно отправляться LLM.

Перед запросом формируется релевантный контекст.

# 12. ИИ NPC

Ключевой принцип:

**LLM не является симулятором мира.**

LLM является системой рассуждения, диалога и выбора сложных действий.

Большинство процессов рассчитываются обычным кодом.

Например:

```text
08:00 проснуться
08:30 поесть
09:00 пойти на работу
13:00 обед
18:00 закончить работу
```

Для этого LLM не требуется.

LLM вызывается при ситуациях вроде:

* необычного события;
* конфликта;
* встречи;
* разговора;
* необходимости сделать выбор;
* изменения жизненной ситуации;
* получения поручения игрока.

---

# 13. Уровни ИИ

Архитектура сразу должна предусматривать несколько уровней.

## Tier 0 — детерминированная симуляция

Самый дешёвый уровень.

Используется обычная игровая логика.

## Tier 1 — маленькая модель

Модель порядка 2–4B.

Используется для:

* классификации событий;
* простых решений;
* выбора следующего действия;
* краткого анализа состояния.

## Tier 2 — основная модель

Модель порядка 8–10B.

Используется для:

* диалогов;
* сложных решений;
* ролевого поведения;
* конфликтов;
* планирования;
* интерпретации поручений игрока.

Такой подход позволит в будущем увеличивать население без линейного роста вычислительных затрат.

# 15. Flux + LoRA

Отдельный существующий сервер Flux + LoRA используется как **визуализатор игрового мира**.

Он не принимает игровые решения.

Пример:

```text
Игровое событие
↓
состояние персонажей
↓
состояние локации
↓
формирование описания сцены
↓
Flux
↓
изображение
```

Изображение должно соответствовать каноническому состоянию мира.

# 16. Режимы отображения

Игра имеет несколько уровней визуализации.

## Карта

Упрощённое отображение острова.

Например:

* карта;
* пиксельные объекты;
* здания;
* персонажи;
* транспорт.

## Режим взаимодействия

При выборе персонажа открывается диалоговая сцена.

Игрок видит:

* персонажа;
* окружение;
* историю разговора;
* варианты действий.

Игрок может выбрать предложенный вариант или написать собственное действие.

## Режим осмотра

Можно запросить визуализацию места.

Например:

на карте:

`дерево`

в визуальном режиме:

`реалистичная сцена от первого лица с конкретным деревом, домом и окружением`

# 17. Постоянная визуальная память

Сгенерированные сцены и объекты сохраняются.

Основная идея:

**мир постепенно приобретает визуальную определённость.**

Если дом уже визуализирован:

* определяется архитектура;
* окна;
* стены;
* мебель;
* расположение объектов.

При последующих генерациях система должна пытаться сохранить эту консистентность.

То же относится к:

* внешности NPC;
* одежде;
* автомобилям;
* интерьерам;
* зданиям;
* природным объектам.

Чем дольше существует сервер, тем меньше элементов приходится создавать с нуля.

# 18. Одежда и внешность

У персонажа существует канонический внешний вид.

Хранятся:

* лицо;
* телосложение;
* волосы;
* особенности внешности;
* одежда;
* аксессуары.

Одежда является реальным игровым предметом.

Если персонаж переоделся, состояние изменяется в базе.

Flux получает именно актуальное состояние.

# 19. Физические объекты

Каждый значимый объект существует отдельно от визуализации.

Например:

```text
Object #8221
type: chair
owner: user_12
location: house_4
room: kitchen
condition: 82
```

LLM не может самостоятельно «придумать», что стул появился.

Она может инициировать действие:

`персонаж хочет купить стул`

После чего игровой сервер проверяет возможность этого действия.

# 24. Причинно-следственная система

Главное требование всей архитектуры:

**никакое значимое событие не должно существовать только в тексте.**

Если NPC говорит:

> Я сломал руку.

Это должно означать, что в состоянии персонажа действительно появилась травма.

Если он говорит:

> У меня нет денег.

Денежный баланс должен это подтверждать.

Если персонаж приобрёл автомобиль, автомобиль должен появиться как объект собственности.

Источник истины — состояние игрового сервера.

Не LLM.

# 33. Первый технический milestone

Первая полноценная демонстрация должна выглядеть примерно так:

1. сервер запускается;
2. существуют 15 NPC;
3. каждый имеет биографию;
4. у каждого есть жильё и работа;
5. проходит игровое время;
6. NPC сами выполняют повседневные задачи;
7. между ними возникают отношения;
8. происходит случайное событие;
9. несколько NPC реагируют на него;
10. один принимает сложное решение через LLM;
11. событие изменяет состояние мира;
12. игрок разговаривает с этим NPC;
13. NPC помнит произошедшее;
14. Flux создаёт визуализацию сцены;
15. через несколько игровых дней последствия события продолжают влиять на мир.

Если этот цикл работает, техническое ядро ВЛ1 существует.

# 34. Основной принцип разработки

Каждую систему следует проверять вопросом:

> Может ли мир существовать без LLM?

Если ответ «нет», значит слишком большая часть игровой логики переложена на языковую модель.

Правильная схема:

```text
Simulation Engine
     ↓
определяет факты

LLM
     ↓
понимает ситуацию и выбирает намерение

Simulation Engine
     ↓
проверяет возможность действия

World State
     ↓
изменяется

Flux
     ↓
показывает результат
```

# 2. Основные архитектурные принципы

## 2.1. Сервер является источником истины

Все факты мира хранятся в игровых структурах и базе данных.

LLM не имеет права напрямую изменять состояние мира.

Пример:

LLM может вернуть:

```json
{
  "intent": "buy_item",
  "item": "bread",
  "reason": "character_is_hungry"
}
```

Но только игровой сервер определяет:

* существует ли магазин;
* есть ли хлеб;
* находится ли персонаж рядом;
* достаточно ли денег;
* открыт ли магазин;
* можно ли совершить действие.

После проверки сервер создаёт событие покупки.

# 9. Simulation Tick

Система работает не единым tick rate.

## Real-time tick

Интервал:


Для:

* движения управляемого игрока;
* активных сцен;
* realtime interaction.

Пример:

```text
5–15 секунд
```

Проверяет:

* текущую задачу;
* достижение цели;
* критические потребности;
* события поблизости.

```text
1 игровая минута
```

Изменяет:

* голод;
* жажда;
* усталость;
* гигиена;
* здоровье.

## Economy tick

```text
1 игровой час
```

## Daily tick

```text
1 игровой день
```

Для:

* зарплат;
* счетов;
* биологических процессов;
* социального summary;
* долгосрочных планов.

# 36. Смерть


* relationships сохраняются;
* событие попадает в память связанных NPC.

Персонажа нельзя просто удалить из базы.

# 45. Utility AI

Большинство повседневных решений можно принимать без LLM.

Для каждого действия рассчитывается utility score.

Пример:

```text
eat = hunger_weight × hunger
sleep = fatigue_weight × fatigue
work = job_requirement × discipline
socialize = social_need × sociability
```

Побеждает действие с наиболее высоким score с учётом ограничений.

---

# 46. Когда вызывается LLM

LLM нужна, если:

* несколько высокоуровневых целей конфликтуют;
* произошло необычное событие;
* требуется социальное решение;
* идёт диалог;
* игрок дал текстовое поручение;
* NPC должен сформировать план;
* нужно интерпретировать сложную ситуацию.

* нет ли отрицательных денег;
* нет ли исчезающих предметов;
* не застряли ли NPC;
* не умерло ли всё население из-за бага;
* не возникли ли невозможные состояния.

# 119. Deterministic Mode

Для debugging simulation желательно иметь:

```text
random_seed
```

Тогда один и тот же мир можно воспроизводить.

LLM результаты отдельно логируются.

# 120. Definition of Done для v0.1

Версия v0.1 считается работающей, если:

1. VPS доступен по домену.
2. Пользователь может зарегистрироваться.
3. Можно создать взрослого персонажа.
4. Существует минимум 10 NPC.
5. NPC автономно живут.
6. Есть потребности и ресурсы.
7. Есть работа и деньги.
8. Есть отношения.
9. Есть event log.
10. Есть долговременная память NPC.
11. NPC ведут диалог через локальную LLM.
12. Игрок может дать текстовое поручение.
13. Игрок может перехватить управление.
14. Можно съездить во Владивосток абстрактным способом.
15. Flux может создать сцену из текущего состояния мира.
16. Картинка сохраняется и привязывается к миру.
17. После перезапуска сервера мир продолжается с прежнего состояния.

# 121. Итоговая архитектурная формула

```text
                PLAYER
                   │
                   ▼
               WEB CLIENT
                   │
                   ▼
              GAME SERVER
                   │
      ┌────────────┼────────────┐
      │            │            │
      ▼            ▼            ▼
 SIMULATION      LLM AI       FLUX
      │            │            │
      └────────────┼────────────┘
                   │
                   ▼
               WORLD STATE
                   │
              PostgreSQL
                   │
              Event History
```

Главное правило проекта:

> **Мир существует сам по себе. AI думает внутри мира, игрок вмешивается в мир, Flux показывает мир — но ни один из этих слоёв не подменяет саму симуляцию.**

Именно это должно быть фундаментом ВЛ1.
