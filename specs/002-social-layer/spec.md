# Спецификация функционала: M2 — Социальный слой (Social Layer)

## Outcome

Добавление социального взаимодействия в мир «ВЛ1: Рейнеке»: NPC теперь имеют долгосрочные взаимоотношения, могут общаться, ссориться и объединяться в организации. Реализовано новое действие `SOCIALIZE`, которое восстанавливает социальную потребность и влияет на уровень симпатии (`affection`). Система полностью детерминирована, расширяет контракт событий M1 и сохраняет полную совместимость с базовым ядром (при `social.enabled = false`).

## Scope

- **Included**:
  - Система взаимоотношений: таблица `relationships` с 8 измерениями (SPEC-V0.1 §29), динамика симпатии (`affection`), события изменения отношений (§30, §59:2809).
  - Социальное действие: `SOCIALIZE` с детерминированным выбором цели, проверкой порогов отказа (`refusal_threshold`) и восстановлением потребности (`social_recovery_per_minute`) (§102).
  - Интеграция с Utility AI: добавление веса `SOCIALIZE.base_utility_weight`, интеграция в реестр действий (`registry.py`) и гейт по порогу `social_action_threshold` (§102).
  - Контракт событий: расширение closed-set из 10 типов (M1) до 13 (добавлены `SOCIAL_INTERACTION`, `RELATIONSHIP_CHANGED`, `CONFLICT`).
  - Минимальные организации: автоматическое назначение лидеров при сиде, таблица `organization_members`, членство в общине и организациях работодателей (§30).
  - Базовые конфликты: триггер конфликта при `affection < -30` после завершения `SOCIALIZE`, увеличение стресса персонажа, фиксированный штраф к симпатии (§98:3554).
  - Инварианты: проверка диапазонов отношений [-100, 100], целостность связей событий и членства в организациях.
  - Конфигурация: новый раздел `social:` в YAML.
  - CLI: флаг `--social` для активации функционала в прогонах.
- **Excluded**:
  - LLM, генерация текстов диалогов, память NPC и сессии общения (M3).
  - Динамика по 7 измерениям отношений (кроме `affection`) — зафиксированы в 0 (отклонение от §10, путь к M3).
  - Романтика, брак, семейные связи, домохозяйства (M3).
  - Направленность отношений (в M2 пары симметричны, `character_a < character_b`) (M3).
  - Физическое насилие, преступления, полиция, месть, траур (M3).
  - Политика организаций: выборы, бюджеты, законы (M3).
  - Runtime-изменение членства в организациях (только при сиде).
  - REST/WebSocket API (M4), Flux/Визуализация (M5).
- **Note**: Данный этап закрывает отложенные в M1 задачи по обновлению отношений (§117) и созданию таблиц `relationships` / `relationship_events` (M1 plan.md:93).

## Requirements

- **R1: Схема взаимоотношений**. Создаётся таблица `relationships` для неупорядоченных пар (`character_a < character_b`), UNIQUE(`world_id`, `character_a`, `character_b`). 8 измерений (trust, affection, respect, fear, anger, attraction, romantic_interest, familiarity) в диапазоне [-100, 100]. В M2 динамическим является только `affection`, остальные зафиксированы в 0 (SPEC-V0.1 §29).
- **R2: События отношений**. Таблица `relationship_events` (id, world_id, character_a, character_b, event_type, impact, event_id FK world_events, game_timestamp) согласно §30.
- **R3: Действие SOCIALIZE**. 
  - Валидность: `social < social_action_threshold` (40.0) И наличие хотя бы одного допустимого кандидата (см. ниже).
  - Выбор цели (детерминирован), три ступени:
    1. **Aggravated seek**: если у актора есть активная вражда (любое отношение с `affection < −30`), целью становится худший враг (сортировка (−affection, id), с refusal-фильтром). Если враг не ко-лоцирован — MOVE к его текущей локации. Обоснование: сидированные feud-пары имеют идеально синхронизированные расписания (M1-детерминизм) и никогда не пересекаются при локальном выборе — конфликт был бы недостижим (проверено трассировкой). §98 требует, чтобы старые конфликты разыгрывались.
    2. **Локальный выбор**: кандидаты (живые в той же локации) сортируются по (`-affection`, `character_id`). Выбирается первый, у которого `affection > refusal_threshold` (-60.0).
    3. **Глобальный seek**: если ко-лоцированных допустимых нет, цель — глобально лучший кандидат (та же сортировка), MOVE к его текущей локации.
    Если допустимых кандидатов нет вообще → действие невалидно → переход к IDLE.
  - Примечание: сортировка по убыванию враждебности означает, что конфликтные пары из feud-диапазона (−60, −30] выбираются ПЕРВЫМИ — это сознательно: сидированные «старые конфликты» (§98) разыгрываются в первую очередь.
  - Длительность: 30 мин.
  - Эффект: восстановление `social` со скоростью `social_recovery_per_minute` (0.5/мин).
  - **Target-locked завершение**: цель фиксируется при валидации (MOVE ведёт к ней); взаимодействие применяется при завершении задачи, если цель всё ещё жива. Ко-локация — свойство момента решения, не завершения. Известное упрощение M2: цель может уехать за 30-минутное окно — взаимодействие всё равно применяется (иначе синхронные расписания делают встречи feud-пар недостижимыми). Если цель умерла — fallback на лучшего ко-лоцированного; если и его нет — задача завершается без событий (восстановление social уже применено).
- **R4: Интеграция Utility AI**. 
  - Формула: `score = weights.social * (100 - social) + SOCIALIZE.base_utility_weight` (utility.py:47-69).
  - Позиция в реестре: после `BUY_ITEM`, перед `IDLE` (registry.py:32-34).
- **R5: Контракт событий**. 
  «The M1 event contract — closed set of 10 types (events.py:10-20, M1 spec R8) — is immutable in names and payload shapes. M2 extends it to a closed set of 13 by adding SOCIAL_INTERACTION, RELATIONSHIP_CHANGED, CONFLICT. Each new type names ≥1 invariant or report consumer. Further additions require a spec change.»
  - `SOCIAL_INTERACTION`: payload `{target_id, duration, affection_delta, affection_after}`.
  - `RELATIONSHIP_CHANGED`: пороги перехода (stranger → acquaintance +10, → friend +50, → conflicted -30) (§59:2809). Payload `{band, affection_before, affection_after}`.
  - `CONFLICT`: payload `{affection_before, affection_after, stress_delta}`.
- **R5a (#61 v2, D2): события смены ролей `ROLE_ACQUIRED` / `ROLE_REVOKED`**. 
  Closed-set каталог расширен 41 → 43 ровно этими двумя типами (миграция не нужна: `WorldEvent.event_type` — String-колонка; `schema_version` не меняется — конвенция репозитория: версия схемы растёт только с новыми таблицами, добавление значений enum событий версию не поднимает — cf. 017: POWER_OUTAGE без bump).
  - **Семантика**: события — НАРРАТИВНАЯ ПРОЕКЦИЯ derive-on-read ролей (`app/social/roles.py`), а НЕ второй источник истины: derive остаётся единственной правдой, события — история; **никакого утверждения о полноте истории ролей** (role-history completeness) события не дают и role-store/синхронизации не создают.
  - **Emission (mutation-backed)**: механика, мутирующая строку-источник роли, делает set-difference identity-кортежей `(role_id, source)` выведенных ролей затронутого персонажа ДО/ПОСЛЕ мутации (identity включает источник, чтобы две роли одного типа из разных источников не совпадали: `org_leader@<org>`) и пишет события в ТОЙ ЖЕ транзакции, что и мутация (атомарно; идемпотентность следует из идемпотентности мутации — переизбрание действующего лидера и повторный отчёт по уже-отправленному преступлению дают пустой diff).
  - **Покрытие (ровно wired-сайты, без претензии на полноту)**: выборы (`policies/org.py` — реальная смена лидера; переход роля org_leader↔org_member проецируется честным diff'ом); криминальный отчёт (`crime/crime.py` — offender приобретается при `unreported→reported`). НЕ эмитирует: резолюция преступления (offender сохраняется: derive даёт роль при `reported|resolved`), истечение «новичка» (clock-driven, mutation site отсутствует — граница 7 дней покрыта только derivation), seed-членство (`world/social_seed.py`).
  - **Payload**: `{role, title, source, reason, character_id, character_name?, cause?, cause_event_id?}`; effective time — колонка `game_timestamp` (в payload не дублируется, по конвенции каталога); `cause_event_id` связывает с причинным событием (ELECTION / CRIME_REPORTED), когда оно очевидно.
  - **Консьюмер/инвариант**: консьюмер — лента `world_events` (нарративная хроника: отчёт прогона и будущие UI/LLM-контексты читают историю смен ролей из событий, текущее состояние — только из derive); инвариант — события порождаются только set-diff'ом на mutation-сайтах и атомарны с мутацией (пин-тесты `tests/m184/`: re-election → 0 событий, rollback → 0 событий, повторный отчёт → без дубликата, resolve → 0 событий, newcomer-expiry → 0 событий). Пины количества 43: `tests/m2/test_chunk_a.py`, `tests/m11/test_chunk_b.py`, `tests/m4/test_chunk_a.py`, `tests/m61/test_roles_context.py`.
- **R5b (#182): партнёрство — явное обоюдное объявление («объявить пару»)**.
  Closed-set каталог расширен 43 → 44 ровно одним типом `PARTNERSHIP_DECLARED` (String-колонка `WorldEvent.event_type`, миграции не нужно). `schema_version` поднят 0.14.0 → 0.15.0 ИЗ-ЗА НОВОЙ ТАБЛИЦЫ (конвенция: версия растёт с новыми таблицами, а не из-за enum — см. R5a).
  - **Авторитетный факт**: таблица `partnerships` (id, world_id, character_a_id, character_b_id, created_at — игровое время; канонический порядок `character_a_id < character_b_id`, CheckConstraint + UniqueConstraint(world_id, character_a_id, character_b_id) — паттерн `relationships`). Роль партнёра выводится ТОЛЬКО из неё (derive-on-read); скаляры настроения (`romantic_interest` и др.) роль не создают.
  - **Механика (агентность игрока)**: `POST /characters/{target_id}/partnership` — инициатор = живой персонаж игрока, цель = NPC. Детерминированные валидации (порядок фиксирован, у каждой свой reason): цель существует (404) / жива / в мире инициатора; цель ≠ инициатор; цель — NPC, не персонаж другого игрока (зеркально `/dialogue/start`); ни одна из сторон уже не в активном партнёрстве (422 с указанием стороны); оба взрослые (age ≥ 18 — конвенция П4: создание игрока требует 18+, `population.min_age: 18`). Согласие NPC — детерминированное правило БЕЗ LLM: affection канонической пары `Relationship` ≥ 25 (v1-константа `PARTNERSHIP_MIN_AFFECTION` в коде эндпоинта — игровая константа v1, не конфиг; канонической строки нет → affection = 0 → отказ). Отказ — игровой исход `200 {"accepted": false, "reason": …}`, а не ошибка; нарушения валидации — 422.
  - **Атомарность**: при согласии строка `partnerships` + `PARTNERSHIP_DECLARED` (payload `{initiator_id, initiator_name, partner_id, partner_name}` — плоские скаляры, время в `game_timestamp`; actor/target — инициатор/партнёр) + ролевые проекции `project_role_events` для ОБОИХ персонажей (`cause="partnership_declared"`, `cause_event_id` → событие-объявление) — ОДНА транзакция; rollback не оставляет ничего.
  - **Синглтон на уровне БД**: уникальные индексы `uq_partnerships_world_a` / `uq_partnerships_world_b` (world_id + character_a_id / character_b_id) гарантируют максимум одну строку на персонажа даже при конкурентных предложениях к одному NPC (разные канонические пары — pair-UniqueConstraint не срабатывает); гонка, прошедшая проверки 422, ловится как `IntegrityError` → rollback → `422 "character is already in a partnership"`.
  - **Роль (derive)**: `{id: "partner", title: "Партнёр {имя}", source: "в паре с {полное имя}", reason: "взаимное объявление пары"}` — синглтон на персонажа, выводится у ОБОИХ; удаление строки удаляет роль (derive — правда). Экземпляр `EXCLUDED_ROLES["partner"]` сохранён как честный guard: БЕЗ строки partnerships роль не изобретается.
  - **НЕ трогается**: математика отношений (`relationships`, дельты, CONFLICT/SOCIALIZE), `InteractionPermission`/consent (согласие на романтические ДЕЙСТВИЯ — отдельный механизм, П1), найм/бизнес/мэр.
  - **v1 без расставания**: строки `partnerships` не отзываются, `ROLE_REVOKED` для партнёрства НЕ эмитируется; расставание — будущий spec-change.
  - **Консьюмеры**: лента `world_events` (report.py группирует generically — изменений не нужно); память NPC (`IMPORTANCE_MAP["PARTNERSHIP_DECLARED"] = 60`, `VALENCE_MAP = 0.7` — по аналогии с RECONCILIATION); UI — кнопка «Объявить пару» в чате, скрывается по роли «Партнёр …» в derive-списке.
- **R5c (#183): encounter-симпатия из диалога — одна дельта на «встречу»**.
  Plain chat игрока с NPC больше НЕ является «только журналом» (ретро-пин #88 «диалог никогда не мутирует отношения» заменён на новую правду): HTTP-диалог (`POST /dialogue/{sid}/message`) применяет РОВНО ОДНУ дельту симпатии на «встречу» (encounter = кластер сообщений внутри окна охлаждения), не на каждое сообщение.
  - **Общий хелпер (паритет by construction)**: правило аффектации SOCIALIZE извлечено в `app/social/affection.py` — `apply_socialize_affection(session, world_id, char_a_id, char_b_id, game_timestamp, settings) -> float`: каноническая пара `sorted([a, b])`, ленивое создание строки `Relationship` (`affection=settings.social.initial_affection, updated_at=game_timestamp`), путь по FRESH-значению (`>= -30 → +2.0`, иначе конфликтный `-5.0`), clamp [-100, 100], запись `affection` + `updated_at=game_timestamp`, возврат RULE-дельты (+2.0/−5.0 по пути) — даже если clamp уменьшил фактическую запись (контракт `social_event_integrity`: delta SOCIAL_INTERACTION ∈ [2.0, −5.0]); честная post-clamp дельта (0 на границе) вычисляется слоем диалога отдельно для поля ответа. SOCIALIZE-ветка lifecycle.py вызывает этот же хелпер (стресс/CONFLICT-событие/org-law/LLM-enqueue остаются в ветке); существующие SOCIALIZE-тесты зелёные без изменений.
  - **Окно охлаждения**: 30 ИГРОВЫХ минут на пару `(character_id, npc_id)` — кодовая константа `DIALOGUE_ENCOUNTER_COOLDOWN_MIN` в `app/api/dialogue.py` (v1: не конфиг). Элигибельность = НЕТ строки `DialogueMessage` ЛЮБОГО прежнего диалогового сеанса этой пары с `game_timestamp` в окне. SQL точен по обеим границам: нижняя — строгое `game_timestamp > now_ts - 30` (сообщение ровно 30 минут назад окно уже не держит); собственные строки текущего обмена исключаются ПО ID (при-hook-времени это единственное видимое сообщение запроса — flushed user-сообщение; npc-ответ добавляется после), НЕ по `game_timestamp < now_ts`: при замороженном игровом времени прежний обмен может делить тот же `now_ts`, и временная верхняя граница его спрятала бы (вторая дельта внутри одного окна — ровно тот баг, который окно предотвращает).
  - **Affection-only by construction**: хелпер читает/пишет ТОЛЬКО `Relationship.affection` и `updated_at`; trust/respect/fear/anger/attraction/romantic_interest/familiarity байт-нетронуты; consent/InteractionPermission не затрагиваются. Побочные эффекты конфликт-пути SOCIALIZE (stress, CONFLICT-событие, org-law, LLM-enqueue) из диалога НЕ эмитятся.
  - **Без мировых событий в v1** (документированное упрощение): дельта диалога НЕ эмитит ни SOCIAL_INTERACTION, ни RELATIONSHIP_CHANGED при пересечении полосы; полосовые события сработают при следующей SOCIALIZE-мутации. Пин m158 «диалог — ноль WorldEvents» остаётся в силе.
  - **Атомарность и паритет путей**: хук выполняется после резолва источника ответа (LLM/fallback дают идентичный результат — parity by construction) и ДО единственного commit эндпоинта — журнал диалога и дельта пишутся одной транзакцией (rollback снимает оба). `dialogue/start` эффект НЕ применяет (встреча = обмен сообщениями, не открытие сеанса).
  - **Ответ API (backward-compatible)**: поле `relationship_effect` — `{"applied": true, "affection_delta": <float>, "affection_after": <float>}` или `{"applied": false}` (окно не истекло); clamp на границе ±100 честно даёт дельту 0.
  - **UI-уведомление**: чат показывает короткую заметку «Симпатия +2» (знак + целое; 0 при clamp — честно) рядом с виджетом отношений (`#chat-rel-note`), только когда `relationship_effect.applied`; иначе заметка очищается/скрывается. Клиент ничего не вычисляет сам — единственный сигнал приходит из ответа сервера.
  - **НЕ трогается**: модели/схема (окно выводится из существующих строк), конфиг, consent.py/InteractionPermission, worker-путь ai/** (R9 спецификации 004-llm остаётся journal-only), романтические скаляры.
- **R6: Организации (минимальные)**. 
  - Лидер: детерминированно выбирается NPC с наименьшим id, чья профессия входит в `leader_titles` организации, либо просто NPC с наименьшим id.
  - Хранение: таблица `organization_members` (organization_id, character_id, role 'leader'|'member', joined_at).
  - Членство: все NPC принадлежат общине, владельцы профессий — соответствующим организациям работодателей.
- **R7: Конфликты**. 
  - При завершении `SOCIALIZE`, если `affection` ЦЕЛИ НА МОМЕНТ НАЧАЛА взаимодействия < −30 (feud-диапазон (−60, −30]) → событие `CONFLICT`: `affection` снижается на 5.0, `character_health.stress` увеличивается на 5 (clamped [0, 100]) ОБОИМ участникам (актор и цель). Без урона здоровью и смерти.
  - Достижимость (адверсариальное ревью + трассировка прогона): refusal-порог −60 допускает выбор сидированных пар (−50); aggravated seek (R3.1) проводит их к взаимодействию даже без ко-локации. Эмпирически (seed 42, 30д): 4 CONFLICT (по 2 на feud-пару), пары выгорают до −60 (refusal) и «замораживаются» — самозатухание, примирение в M2 невозможно (M3).
  - Сидирование: 2 пары конфликтов (`affection = -50`) создаются при генерации мира через seeded RNG (детерминировано) (§98:3554).
  - Обычный delta: +2.0 при успешном взаимодействии, clamp [-100, 100] (диапазон — §29).

  Дополнение к `needs.recovery_rates`: `SOCIALIZE: {social: 0.5}`.
- **R9: Инварианты**. 
  - `relationship_range`: все 8 измерений ∈ [-100, 100], отсутствие self-pairs, `character_a < character_b`.
  - `social_event_integrity`: актор и цель события существуют в одном мире, актор ≠ цель, валидная локация.
  - `relationship_event_link`: каждый `relationship_events.event_id` существует в `world_events`.
  - `org_membership_integrity`: члены существуют; лидер организации является её членом.
  - `no_impossible_states`: расширение — `stress` ∈ [0, 100].

## Non-Functional Requirements

- **Performance**: Wall-time ≤ 60 с для прогона 30д/20NPC с включенным `social.enabled = true`.
- **Determinism**: Два прогона с одним seed должны давать идентичную последовательность `world_events`.
- **Regression**: При `social.enabled = false` поведение мира должно быть идентично M1 (AE5). Все тесты M1 AE1-AE8 должны проходить без изменений.

## Acceptance Evidence

- **AE1**: `vl1 simulate --days 30 --population 20 --seed 42 --social` → exit 0; все новые инварианты пройдены; `SOCIAL_INTERACTION` ≥ 60, `CONFLICT` ≥ 2, `RELATIONSHIP_CHANGED` ≥ 10; population_alive == 20; wall-time ≤ 60 с.
- **AE2**: 7-дневный прогон/20 NPC (social-on) зелёный (`SOCIAL_INTERACTION` ≥ 14).
- **AE3**: Unit/интеграционные тесты обновлений отношений (§117): детерминированный delta, clamp ±100, отказ ниже -30, триггер конфликта при завершении, событие перехода между bands ровно один раз.
- **AE4**: Детерминизм: два идентичных seed → идентичный лог; разные seed → разные логи.
- **AE5**: Регрессия M1: дефолтный конфиг (social off) 30-дневный прогон воспроизводит вектор событий M1 в точности (SALARY_PAID == 600, SUPPLY_ARRIVED == 30, идентичная последовательность `world_events`); AE1-AE8 M1 пройдены.

## Risks

- **SOCIALIZE dominance**: При большом количестве NPC в поселении (до 200) действие `SOCIALIZE` может стать доминирующим, вытесняя другие потребности.
- **Feud-динамика**: конфликтные пары деградируют до −60 за ~2 стычки и замораживаются; примирение невозможно в M2 (осознанное ограничение, M3). Сортировка «самый ненавистный первым» концентрирует ранние SOCIALIZE на feud-парах — AE1 CONFLICT ≥ 2 ожидаемо достижим, но наблюдаемая картина первых дней будет конфликт-тяжёлой.
- **Performance headroom**: Текущий baseline M1 (50.06 с) оставляет мало запаса до лимита в 60 с; риск срабатывания триггера R10.
- **Pydantic defaults**: Требуется осторожное обновление моделей Pydantic для поддержки новых полей в `conftest`.
- **Float determinism**: Различия в вычислениях float на разных платформах могут повлиять на детерминизм отношений (смягчено использованием фиксированных дельт).
- **§10 Tension**: Зафиксировано отклонение от SPEC-V0.1 §10 (использование набора колонок вместо одного числа) для обеспечения пути развития в M3.
