# Feature Specification: M1 — Simulation Core (без AI)

## Outcome

Работающий без внешних сервисов детерминированный headless-мир «ВЛ1: Рейнеке»:
одна команда запускает мир из 20 автономных NPC, которые проживают 30 игровых дней
(цель milestone — минимум 7 дней, §101 SPEC-V0.1) без ошибок, без «застреваний»,
с полной историей событий (event log) и деньгами через ledger, воспроизводимо
при одном и том же seed. Наблюдаемый результат — JSON-отчёт прогона, в котором
все инварианты §118 пройдены, и зелёный тестовый контур §117.

## Scope

- Included:
  - Игровое время: world_clock, игровые минуты как базовая единица, уровни тиков
    needs/character/economy/daily (SPEC §8–9).
  - Персонажи: каноническая запись (§10), профиль (§11), traits (§12),
    потребности (§13), здоровье и смерть (§14, §36).
  - Локации и иерархия (§18), граф смежности, движение по графу с длительностью
    в игровых минутах (без pathfinding).
  - Action system: lifecycle, validators, реестр из 7 действий
    (SLEEP, EAT, DRINK, WORK, MOVE, BUY_ITEM, IDLE), tasks-очередь (§40–43),
    Utility AI для выбора действий (§45).
  - Needs decay/restore и их влияние на здоровье.
  - Экономика: accounts/transactions (только через ledger), зарплаты, магазин
    с фиксированными ценами, ежедневная абстрактная поставка еды/воды (§73–74, §25).
  - Инвентарь: предметы-объекты (§21–22), еда как предмет с nutrition (§24),
    вода как ресурсный баланс поселения (§23, §25).
  - Event log world_events (§58–59) — append-only.
  - NPC generation: детерминированный генератор (имена, пол, возраст 18+, traits,
    templated-профиль, профессия, жильё, стартовые деньги/инвентарь) (§96–99, без
    социального графа и LLM).
  - Headless CLI `simulate --days N --population M --seed S`, инварианты §118,
    JSON-отчёт, дневные снапшоты (§100).
  - Конфигурация YAML: все игровые параметры, без хардкода (§116).
  - Тесты §117 (применимые к M1) + интеграционные 7д/20NPC и 30д/20NPC (§118),
    детерминизм по seed (§119).
- Excluded:
  - LLM/AI любого уровня, AI Gateway/Queue/Worker (M3, §103; конституция П2).
  - Relationships, социальный граф, социальные действия (M2, §102).
  - Players: регистрация, web-api, WebSocket, control_mode (M4, §104).
  - Flux/визуализация (M5, §105).
  - Владивосток и внешние поездки TRAVEL_EXTERNAL (M6, §106) — поставка из
    города абстрагирована ежедневным событием SUPPLY_ARRIVED.
  - Pathfinding, realtime-tick (250–1000 мс, §9), электричество/blackout (§26),
    здания как отдельная сущность (§20), construction/разрушение (§75–76),
    погода (§71), законы/преступления (§32–35), память NPC (§55–57), skills (§15),
    hygiene-цикл (восстановление гигиены — M2), тесты §117 «relationship updates»
    (M2) и «AI JSON validation» (M3).
  - Миграции схемы (Alembic) — схема новая, деплоев нет; вводится при первом
    изменении схемы живого мира.
- Protected boundaries:
  - Конституция П1: источник истины — состояние в БД; никакое значимое событие
    не существует только в тексте.
  - Конституция П2: мир обязан жить без LLM; весь выбор действий M1 — Tier 0.
  - Конституция П3: все значимые изменения — в world_events; все денежные
    изменения — только через transactions; прямые мутации балансов запрещены
    (включая начальные балансы при бутстрапе).
  - Конституция П4: все персонажи 18+ по серверному полю age; никакого
    романтического/сексуального контента в M1.
  - Действие → состояние мира → реакция → последствия (П5): каждое действие
    меняет БД и оставляет событие.
  - Модули вне M1 (relationships, ai, visuals, auth, admin) не создаются и не
    импортируются из M1-кода.

## Requirements

- R1: Tick engine. Мир продвигается дискретными игровыми минутами; при пересечении
  границ запускаются needs tick (1 игровая минута), character tick (1 игровая
  минута, лёгкая фаза), economy tick (1 игровой час), daily tick (1 игровой день).
  Headless-режим не зависит от wall-clock; is_paused останавливает продвижение.
  (SPEC §8–9, §101)
- R2: Determinism. Прогон однозначно определяется (config, seed, days, population);
  случайность worldgen — из seeded RNG; runtime-правила детерминированы; порядок
  обработки персонажей — по возрастанию id; tie-break utility — по порядку
  реестра. (SPEC §119)
- R3: Персонажи и генерация. `simulate --population M` создаёт M NPC: уникальные
  имена, пол, возраст ≥ 18 (серверная проверка), traits −100..+100, templated
  профиль, профессия с расписанием и зарплатой, жильё с capacity, стартовые
  деньги (через ledger) и стартовый инвентарь. (SPEC §10–12, §96, §99; конституция П4)
- R4: Needs. hunger/thirst/energy/social деградируют со временем по конфигурируемым
  ставкам в диапазоне 0–100 (100 = удовлетворена); SLEEP/EAT/DRINK восстанавливают
  соответствующие потребности; критический голод/жажда снижает health; health 0 →
  CHARACTER_DIED, alive=false, прекращение задач, имущество уходит на склад общины
  с событием. (SPEC §13–14, §24, §36, §116)
- R5: Action system. Каждое действие проходит REQUEST→VALIDATE→(RESERVE)→START→
  PROGRESS→COMPLETE→EMIT EVENTS или FAIL/CANCEL/INTERRUPT; у каждого типа действия
  есть validator; у персонажа максимум одна active-задача; Utility AI выбирает
  следующее действие по score = Σ(вес × дефицит потребности) среди валидных;
  MOVE порождается преусловиями и перемещает персонажа по графу за сумму
  travel_minutes рёбер. (SPEC §40–45)
- R6: Economy. Балансы существуют только в accounts; любое изменение — транзакция
  с amount>0, ссылкой на событие и balance_after; зарплата — daily tick от счёта
  работодателя; покупка — атомарный обмен «деньги↔предмет» с событиями
  SALARY_PAID/PURCHASE/ITEM_TRANSFERRED; начальные балансы — mint-транзакции.
  (SPEC §73–74; конституция П3)
- R7: Inventory/resources. Предметы создаются, передаются и потребляются только
  через API inventory с событиями ITEM_TRANSFERRED/ITEM_CONSUMED; еда имеет
  nutrition; вода — ресурсный баланс поселения, расходуется DRINK, пополняется
  SUPPLY_ARRIVED. (SPEC §21–25, §58)
- R8: Event log. Все перечисленные в R3–R7 изменения пишутся в world_events
  (id, world_id, game_timestamp, event_type, actor_id, target_id, location_id,
  payload) через append-only API; id монотонен. (SPEC §58–59)
- R9: Мир и локации. Бутстрап создаёт мир reineke_001, иерархию локаций §18,
  граф смежности с travel_minutes, организации (община, магазин), ресурсный
  баланс воды, jobs и housing; capacity локаций соблюдается. (SPEC §7, §16–18, §99)
- R10: Headless CLI и инварианты. `simulate --days N --population M --seed S
  [--config PATH] [--out PATH]` выполняет прогон и проверяет: нет отрицательных
  балансов; консервация предметов и воды; нет задач старше max_duration или с
  истёкшим ends_at; смертность ≤ порога и каждая смерть объяснена событием;
  needs/health в [0,100]; ссылки на локации/персонажей валидны. Нарушение —
  ненулевой exit-код и отчёт с diagnostics. (SPEC §118)
- R11: Снапшоты и persistence. Состояние мира хранится в SQLite-файле; в конце
  каждого игрового дня создаётся снапшот-копия с записью в world_snapshots;
  после перезапуска мира симуляция продолжается с сохранённого состояния.
  (SPEC §100, §120.17)
- R12: Конфигурация. Все игровые параметры (ставки decay, веса utility,
  длительности действий, цены, зарплаты, размеры популяции и локаций, интервалы
  коммитов и снапшотов, пороги инвариантов) читаются из YAML (§116); код не
  содержит игровых констант.

## Non-Functional Requirements

- Security: нет сетевых интерфейсов и внешних сервисов; вход — только локальный
  config/CLI; секретов нет. П4 соблюдён конструктивно (возраст — серверное поле).
- Reliability: прогон 30д/20NPC завершается без необработанных исключений; любое
  падение между коммитами теряет ≤ 1 игрового часа состояния (воспроизводится от
  seed); нарушение инвариантов обнаруживается автоматически.
- Performance: прогон 30 игровых дней / 20 NPC ≤ 60 c wall-clock на эталонной
  машине песочницы (цель ≤ 10 c); прогон 7 дней ≤ 15 c.
- Operability: отчёт прогона в JSON + stdout-сводка; exit-коды 0/2/3; логи
  содержат world_id и game_timestamp (основа §88observability).
- Compatibility: SQLAlchemy 2.0 declarative, портируемые типы (INTEGER-время,
  INTEGER-деньги, JSON-строка), world_id в каждой записи состояния — миграция на
  PostgreSQL/PostGIS (§28) = connection string + dialect-типы; Python ≥ 3.12;
  управление зависимостями через uv.

## Acceptance Evidence

- AE1: `uv run vl1 simulate --days 30 --population 20 --seed 42` завершается с
  exit 0; отчёт содержит все инварианты R10 в статусе pass; alive-персонажи
  присутствуют; счётчики world_events ненулевые.
- AE2: `tests/integration/test_headless_7_days_20npc.py` зелёный: 20 NPC, 7
  игровых дней, ни одной ошибки; цель §101 выполнена.
- AE3: `tests/integration/test_headless_30_days.py` зелёный (интеграционный, §118).
- AE4: `tests/integration/test_determinism.py`: два прогона с одним seed дают
  идентичные последовательности world_events (контрольный хэш); прогоны с разными
  seed дают разные. (§119)
- AE5: Полный набор тестов §117 (применимые к M1 строки таблицы маппинга в
  plan.md) зелёный: economy conservation, inventory transfer, death state,
  needs decay, action validation, world clock, travel completion, event generation.
- AE6: Тест консервации ledger подтверждает: после произвольного прогона
  Σ(balances) == Σ(mint) + Σ(дельты транзакций); ни одной транзакции с amount ≤ 0.
- AE7: Тест конфигурации: изменение needs decay / весов utility в YAML закономерно
  меняет метрики прогона — параметры не захардкожены (§116).
- AE8: Обязательные quality gates проекта зелёные на финальном head (lint + тесты;
  целевая команда фиксируется в tasks.md T-verification после починки gate-конфига,
  см. Open Questions Q3).

## Риски (доп. секция сверх шаблона)

- RISK-1: Дрейф схемы SQLite→PostgreSQL/PostGIS — смягчён портируемыми типами и
  запретом dialect-специфики (см. NFR Compatibility; plan.md Risk Profile).
- RISK-2: Калибровка decay/весов может дать вымирание или «вечный сон» — смягчено
  тем, что все ставки в config, инвариант смертности в отчёте, kitchen-stock
  исключает голодную спираль.
- RISK-3: Скрытая зависимость от порядка обхода сломает детерминизм — смягчено
  правилом «итерация только по отсортированному id» и AE4.
