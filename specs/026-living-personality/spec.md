# Контракт v1.0 — Living Personality / Presence-driven initiative

**Статус:** нормативный целевой контракт, согласованный владельцем в #396 и допущенный к коммиту #397. Текущий runtime сохраняет прежнюю модель до согласованного cutover. Единый handoff #398–#405; [основная спецификация](../../docs/SPEC-V0.1.md) §2, §12, §60–62, §104 ссылается на этот документ. Не объявляет код реализованным. Числовые значения ниже — инженерные defaults v1, не обещания измеренной производительности. Изменять их только версионированным контрактом/конфигурацией.

## 1. Инварианты
- Один непрерывный мир, одна личность, один персонаж, одна авторитетная симуляция. NPC и персонаж игрока в его отсутствие используют общий планировщик.
- Присутствие определяет право инициировать действие, не характер. Нет пользовательских AUTONOMOUS/GUIDED/DIRECT и выбора режима при создании. Игрок может наблюдать или командовать в одной и той же игровой сессии. Активное присутствие даёт исключительную инициативу над новыми действиями своего героя; чужие NPC остаются независимы. Полный контроль не означает обход фактов мира, consent, ресурсов, прав или системных последствий.
- Личность/потребности/желания/цели/намерения/задачи/события различны. Жизнь полноценна при нуле целей. AI не авторитет состояния. LLM предлагает структурированные намерения, engine валидирует и применяет; Flux визуализирует, не устанавливает факт. При выключенной LLM работает deterministic fallback.
- Не более одной активной физической задачи на персонажа. Допустима явно принятая цепочка шагов, но каждый следующий шаг проверяется повторно. Все действия, включая AI-worker, цели, MOVE-пререквизиты, IDLE preemption, строительство и мгновенные операции, проходят единый арбитр инициативы (с учетом типа операции) и доменные валидаторы; нет прямой записи задач из LLM.
- Авторитетный результат — committed transaction и связанное событие/состояние. Принятое пожелание, текст, preview, запрос и ожидание не равны результату.

## 2. Личность: данные, редактирование и описание (#398, #385, #378)
Единственная каноническая структурированная модель на персонажа: версия схемы, четыре целочисленные шкалы 0..100, 0..3 уникальных идентификатора интересов, источник (preset/custom/biography/import), необязательная ссылка на происхождение пресета, внутренняя модель и её версия. Историческая биография — отдельный текст пользователя (существующие лимиты и правила). Жизненный вектор = интересы + характер + устойчивые стремления; не класс, не профессия, не ограничение действий.

| Пресет (ID) | Общительность | Открытость | Организованность | Амбициозность | Интересы по умолчанию |
|---|---:|---:|---:|---:|---|
| socialite | 90 | 85 | 20 | 40 | Общение, Развлечения, Музыка |
| creator | 20 | 80 | 45 | 65 | Творчество, Музыка, Саморазвитие |
| entrepreneur | 70 | 65 | 90 | 95 | Бизнес, Саморазвитие, Общение |
| homebody | 30 | 20 | 65 | 25 | Дом и быт, Природа, Отношения |
| explorer | 55 | 95 | 25 | 60 | Путешествия, Природа, Саморазвитие |
| romantic | 80 | 60 | 35 | 40 | Отношения, Общение, Творчество |

Это исходная калибровка из согласованного UX, числа допускают балансировку тестами #401. Нейтральный custom: 50/50/50/50, 0 интересов. Каталог интересов v1: communication, entertainment, music, creativity, business, home, relationships, nature, travel, learning, craft, sport; русские названия как в UX. Новая запись интереса не регистрирует новое действие. Системные пресеты readonly; пользовательские аккаунтные пресеты — именованные сохранённые комбинации, CRUD только владельцем, уникальное имя в пределах аккаунта, копирование системного без изменения оригинала. Персонаж получает независимый снимок; редактирование/удаление пресета после создания не меняет его.

Четыре шкалы видны только в раскрываемой настройке, готовый пресет — быстрый путь. Изменение шкал/интересов мгновенно пересчитывает детерминированное описание: диапазоны 0..30 / 31..69 / 70..100; нейтральное словесное описание без выдумывания образования, пола, профессии, места рождения, прошлого. Ручной выбор всегда доступен. Свободная биография → явный запрос локальной LLM → валидированный черновик с предложением шкал/интересов и пояснением → принятие пользователем; устаревший результат (revision mismatch) не применяется. Не делать LLM вызов на каждом slider input. При сохранении каноническое описание пересчитывается сервером из подтвержденных параметров; литературное описание опционально, не источник механики. Никаких скрытых traits на UI. 

Существующие trait keys -100..100: sociability = 2*S-100, curiosity = 2*O-100, discipline = 2*P-100; ambition хранить как собственную нормализованную характеристику (не выводить из materialism). Внутренние признаки формируются из подтвержденных данных и версии правил; не выводить агрессию, эмпатию, ревность, риск или нравственность из одной оси. Не перезаписывать независимые существующие traits. Правило хранения: четыре оси — canonical personality record; соответствующие legacy traits — производная проекция либо read-through, не второй редактируемый источник истины. Для старых персонажей сначала derive 0..100 из существующих трёх ключей (round((trait+100)/2)), неизвестные/ambition=50, интересы пусты; сохранить оригиналы, биографию, историю. Не запускать массовую LLM-генерацию или случайную миграцию. NPC используют те же поля и fallback. Долговременное изменение личности после создания и обучение на опыте — не MVP; память и текущие желания уже могут менять поведение.

## 3. Присутствие и границы времени (#399)
Это внутренний server state, не режим UX:
| Состояние | Условие | Инициатор новых действий |
|---|---|---|
| NPC | Нет владельца | AI |
| ABSENT | Владелец есть, нет действующего lease | AI |
| PRESENT | Живой герой, действующий lease игровой сессии | Игрок; AI только предлагает |
| UNAVAILABLE | Мёртвый герой или герой недоступен для действий по системным правилам | Нет новых команд; системные последствия продолжаются, не оживлять |

Lease — серверная запись на (world, character, owner, authenticated session generation, lease epoch); отдельные client instance ID вкладок. Старт: после auth + выбора/создания живого собственного персонажа при входе на игровую поверхность, до выдачи actionable snapshot/первой команды. Не приобретать lease на landing/login/creator, при чтении публичного профиля, visual preview или просто наличию cookie. Игровые подстраницы и фоновые вкладки с живым heartbeat сохраняют участие. Первый join атомарно фиксирует boundary игрового времени G, event cursor, epoch; ответ — фактическое место/задача и права. Действующие команды обязаны содержать текущий authority epoch + idempotency key (или эквивалентный серверный fencing token). Время lease серверное UTC real-time, не client clock и не game_timestamp. Defaults: heartbeat каждые 10 секунд, срок 45 секунд от последнего принятого heartbeat; точка истечения включительно. Lease не зависит от timescale или pause. Несколько вкладок одного владельца: одна authority epoch, несколько живых участников, одна последовательная очередь запросов; последнее успешное состояние читается всеми, дубли идемпотентны. Heartbeat renew не меняет epoch, stale client не возрождает старую аренду. Нет зависимости только от WS disconnect.

| Переход | Обязательное поведение |
|---|---|
| ABSENT → PRESENT | Сериализовать с tick; завершить только реально наступившие границы старых задач до G, fence новые AI-задачи, сохранить уже активную задачу; не стартовать ещё не начатые AI-шаги, пометить их отменёнными/возвращёнными в намерение с причиной takeover; никакой телепортации. |
| PRESENT → PRESENT (новая вкладка/reconnect до TTL) | Присоединить/renew participant; сохранить epoch/задачу/цели, не повторять сводку и takeover, не сбрасывать часы. |
| PRESENT → ABSENT | Явный выход из игры последнего участника, logout соответствующей сессии или истечение последнего lease: увеличить epoch, зафиксировать G/event cursor, возобновить AI с учётом текущих задач и целей; не отменять принятое игроком действие из-за выхода. Logout/all-session revocation отзывает соответствующие lease. |
| ABSENT → PRESENT после TTL/restart | Новый epoch, revalidate, snapshot актуального состояния. Не повторять старые команды/LLM ответы. |
| PRESENT/ABSENT → UNAVAILABLE | Смерть или системная недоступность героя: отозвать право команд, применить существующие системные правила; при восстановлении доступности заново определить presence, без неявного восстановления lease. |
| PRESENT → ABSENT при отзыве авторизации | Отозвать соответствующие lease; если других действительных участников нет, живой доступный герой продолжает автономную жизнь. Заблокированный аккаунт не получает командного права. Удаление героя — штатный lifecycle, не перевод в AI. |

Закрытие одной вкладки best-effort leave её instance; другие остаются. При потере сети игрок до восстановления не отправляет команды «вслепую»; UI показывает потерю связи и повторно получает lease/snapshot, не replay mutating requests без idempotency. Перезапуск сервера: invalidate все process leases и bump generation, не считать открытый cookie присутствием; повторный join обязателен. Если real clock отступил/недостоверен, не продлевать спорное право; обработать с monotonic deadline в процессе и fail closed на stale epoch. Одно место сериализации DB transaction для lease boundary, проверки authority, enqueue/activation и commit эффекта; read-check вне транзакции недостаточен. Повтор запроса с тем же key/epoch возвращает тот же записанный outcome, не toggle/платёж второй раз; conflicting payload → отказ. Отложенный ответ LLM с прежним epoch/revision не запускает действие.

**Catch-up:** текущий live tick двигает game time только при работающем runtime и не восполняет downtime по wall clock. MVP сохраняет это правило: сервер/машина выключены — игровой мир не продвигается, сводка честно указывает отсутствие данных; отдельная будущая задача для downtime catch-up. Внутренний catch-up при больших game steps сохраняется, но режется на границах join/leave/expiry и creation; ни один новый autonomous шаг не стартует внутри PRESENT интервала, ни одна player команда не backdate до её приёма. Истечение lease обрабатывается на первой сериализованной серверной границе текущего game clock, не ретроактивно по wall time; при pause game G может совпасть, порядок задаёт boundary sequence/epoch. Не реконструировать деятельность за период неизвестного присутствия.

## 4. Арбитр, задачи и правила прерывания
Порядок: системные события/обязательные последствия → завершение уже наступившего действия → валидная явная команда активного игрока / принятое пожелание → продолжение явно принятой цепочки → при ABSENT/NPC валидируемая AI-инициатива. У online нет тайного «аварийного AI» даже при голоде: предупреждение, последствия engine продолжаются. Системные перемены (здоровье, погода, чужие действия, enforced ограничения) не являются инициативой героя. При отсутствии игрока жизненно важные потребности имеют приоритет над стремлениями. Любое принятие нового шага проходит проверку actor/world/alive/ownership/epoch/source/доступности/текущего состояния/ресурсов. Ошибка нового действия не отменяет текущее.

| Тип | Планируемое (ещё не начато) | Активное при входе/новой команде |
|---|---|---|
| IDLE | Отменить AI-шаг при takeover | Прерываемо сразу; сохранить факт elapsed, не запускать старый IDLE preemption в PRESENT |
| SLEEP / EAT / DRINK / WORK / SOCIALIZE | Не запускать новые AI-шаги при PRESENT; player chain отдельно | Продолжить по умолчанию; игрок может явно прервать после предупреждения, применив уже заработанное постепенное восстановление до G один раз, без completion-only еды/зарплаты/отношений за незавершённый шаг. Не откатывать ранее committed эффекты. |
| MOVE | Отменить незапущенный AI MOVE и зависимые AI-шаги | До внедрения промежуточных координат не прерывать активный MOVE: существующая модель меняет location_id при completion. Показать «В пути», разрешить осмотр/чтение; новую физическую команду отклонить BUSY, предложить после прибытия, без телепортации. |
| BUY_ITEM | Отменить незапущенный AI шаг | Непрерываемая активная транзакция v1; завершить/отклонить по валидатору. Покупка/ledger и владение атомарны. Не считать заказ покупкой до commit. |
| TRAVEL_EXTERNAL / CONSTRUCT | Не запускать неразрешённую AI-задачу; сохранить принятые player шаги | Непрерываемы v1 до штатной завершённости/отказа; не менять ресурсы или место раньше фактического перехода. Проверить реальные фазы/расходы и запрещённые сценарии, не придумывать промежуточную позицию. |
| Уже terminal | Не перезапускать | Не изменять completed/failed/cancelled; корректировка только существующей админ-процедурой. |

Не принуждать к отмене текущей задачи при входе. Явная команда физического действия при busy: UI предлагает «Продолжить» или «Прервать и выполнить» только если текущий тип допускает отмену. Сервер проверяет оба действия и atomic preempt, в противном случае возвращает BUSY/NOT_INTERRUPTIBLE без изменения. Нет бесконечной очереди неявных пользовательских команд; существующая подтверждённая dependency chain связана chain_id и источником, повторно проверяется при activation. При отмене prerequisite отменить dependent chain, связанный goal/wish обновить как interrupted/queued при допустимом будущем повторе, не оставлять ложный active. Не реанимировать cancelled task. Если goal активен и источник прежней AI-цепочки прерван входом, не терять цель: переоценить при ABSENT или после явного согласия. Контракт не добавляет player pause/resume task schema без отдельного согласования; «прервать» = terminal cancelled с причиной и сохранением уже committed эффектов. Не выдавать фиктивную зарплату/еду/социализацию за неполный шаг; существующие gradual markers restored_until сохранить. Системный fail (смерть, невозможность, срок) применяет штатные правила даже при PRESENT.

## 5. Матрица прав и аудит текущих путей
Обозначения P = подтверждённое активное присутствие владельца; A = NPC/отсутствие владельца (AI разрешён только для явно поддерживаемых engine действий); R = чтение с действующими правами; — = запрещено. Все правила ниже дополнены существующими доменными ограничениями и правами. Вход в UI не даёт админские полномочия. Вне P команда пользователя не принимается до join; чтение вне игровой сессии допустимо по существующему auth. 
| Операция | P | A | Текущий путь / граница |
|---|---|---|---|
| Карта, LOD, remote inspect, инвентарь/профиль/события | R | R с правами | GET /world, /locations, /characters, /inventory, /actions/{id}; чистый read не приобретает lease, не MOVE |
| Пойти/есть/пить/спать/работать/общаться/покупка в магазине | Явная команда | Валидируемая AI-задача из каталога | POST /actions; /travel/plan; /scene/act (look чистый read отделить от mutating веток; wear/take_off мгновенные). Убрать legacy 409 по control_mode, заменить authority guard. |
| Поездка за пределы острова | Явная команда | Только существующая явно поддерживаемая возможность; иначе — | TRAVEL_EXTERNAL via /actions; purpose/стоимость/ресурсы проверяются. Не открывать AI внешние поездки автоматически. |
| Строительство | Явная команда | — в MVP | POST /build сейчас создаёт planned напрямую; общий арбитр/chain validation, не обходить очередь. |
| Рынок: offer/list/cancel/buy | Явная подтверждённая операция | — новые операции в MVP; существующий NPC/system lifecycle не ломать | POST /market/offers, /{id}/buy, /{id}/cancel — atomic service/ledger, не очередь BUY_ITEM. Идемпотентность. Сохранить фактические правила местоположения (не вводить обязательный магазин для marketplace без спеки). |
| Экипировка предметов | Явная операция | Только будущая явно поддержанная AI-возможность | POST /wear и scene wear/take_off используют один сервис; явный desired worn state/idempotency вместо повторного toggle по retry. |
| Чат, письма, романтика, партнёрство | Явная инициатива | Другой NPC/системный ответ согласно действующим rules; не писать от игрока online | /dialogue/start, /dialogue/{id}/message, /messages, /interactions/romantic, /characters/{target}/partnership; preserve privacy, возраст, consent, существующие проверки контакта/присутствия. Не считать все формы общения задачей SOCIALIZE и не обещать AI переписку за игрока offline в MVP. |
| Цель/желание игрока | Создать/изменить/отменить/уточнить | AI читает и выбирает приоритет, не авторизует цель вместо пользователя | /characters/{cid}/goals, /desire, /desire/interpret, DELETE /desire. Развести игрока и персонажа; interpretation без изменения факта. |
| Принять/отложить пожелание | Явное решение | Автономный планировщик сам решает, не replay старое согласие | новый сервис #400; принятие повторно валидирует доступность; не создаёт duplicate action |
| Настройки/visual/preview/creator | Существующие права; не физическое действие | Существующие права, без захвата инициативы | /visual/*, /characters/draft, /characters/{cid}/outfit (presentation), auth, profile/settings. Не выдать portrait preview за экипировку или прогресс. |
| Системные процессы / admin | По существующим полномочиям | По существующим полномочиям | tick, health, external systems, admin pause/resume/timescale/teleport/cancel и др.; обход игроком невозможен. Admin cancellation тоже синхронизирует цепочки, goal/wish и события. |

Мгновенные операции не превращать искусственно в длительные задачи. При активной физической задаче чтение и неперемещающие операции разрешены, только если существующий доменный валидатор/фактическая совместимость допускают; отсутствие такой проверки не лицензия на новые физические эффекты. Правило совместимости v1: рынок (atomic offer/buy/cancel), экипировка и коммуникация допустимы параллельно физической задаче лишь если их действующие доменные проверки выполняются, операция не создаёт второй physical task и не противоречит выполняемой задаче (например, нельзя расходовать зарезервированный ресурс). CONSTRUCT — физическая задача, не запускать параллельно; при конфликте BUSY с объяснением, не автоматическая отмена. Для неизвестной совместимости fail closed до явного решения в #399. Не запрещать удалённый marketplace только из-за того, что герой занят; действующие правила доступа сохраняются. Consent и решения других персонажей не заменяются управлением владельца. Все новые mutating actor endpoints обязаны декларировать action/metadata/system class и пройти тот же gateway. Старый /control: на этапе migration disabled feature возвращает понятный LEGACY_CONTROL_REMOVED/409 без изменения; после согласованного cutover удалить из UX/API по совместимости.

**Аудит обнаруженного кода main:** [API](https://github.com/MostDef2000/lifesim/blob/main/backend/app/api/app.py#L1001) имеет режимный guard в actions/travel/scene, но отдельные market/wear/build/dialogue пути его не используют. [lifecycle](https://github.com/MostDef2000/lifesim/blob/main/backend/app/actions/lifecycle.py#L785) проверяет DIRECT после activation и IDLE preemption; goal conversion отдельно создаёт MOVE+action. [AI worker](https://github.com/MostDef2000/lifesim/blob/main/backend/app/ai/worker.py#L118) напрямую создаёт SOCIALIZE status STARTED с req.game_timestamp; это обязательный migration gap: нормализовать статусы, заменить на общий arbiter/enqueue, не применять старые запросы задним числом. [live ticker](https://github.com/MostDef2000/lifesim/blob/main/backend/app/api/ticker.py#L40) использует game steps, не wall-downtime replay. [CharacterTrait](https://github.com/MostDef2000/lifesim/blob/main/backend/app/characters/player.py#L166) инициализируется 0; [utility](https://github.com/MostDef2000/lifesim/blob/main/backend/app/actions/utility.py#L10) использует needs. Это исходные наблюдения, не результаты тестов или exhaustive runtime audit. Реализация должна искать ВСЕ записи CharacterTask/state в дереве, включая тестовые/legacy/дополнительные сервисы, и доказать отсутствие обходов.

## 6. Мотивация, намерения и собственные мысли (#400, #401)
- Personality: устойчивые предпочтения, не приказ. Needs: факты, меняются движком. Personal aspiration: долгосрочное собственное стремление, может быть недостижимым в текущем мире. Player goal: явно введённая необязательная цель, не подменяет личность. Intention/wish: конкретное предложение с причиной и привязкой к доступному кандидату; action/task: только валидированное исполнение. 
- Для v1 один активный долгосрочный player desire по текущей семантике CharacterDesire (0 допустимо), краткосрочная очередь CharacterGoal отдельно; собственные aspirations/wishes отдельно, не использовать тот же active row. Игрок может сменить/отменить долгосрочную цель; история сохраняется. Existing CharacterDesire source_text введён игроком, мигрировать именно как player goal, не как собственное желание. CharacterGoal сохраняет источник, task_id и сроки; новая цель не запускает автоматический шаг при PRESENT, даже при высокой важности. 
- Кандидат содержит actor, action_type/grounded params, source, reason (проверяемые факты, не скрытые мысли других), created_game, valid_until_game, authority_epoch, semantic_revision/context token и dedup key. Не привязывать идентичность цели к отформатированному LLM-тексту. Неисполняемое стремление может быть видно как aspiration без кнопки выполнения. 
- Wish lifecycle: proposed → accepted/requested → running → completed/failed/cancelled (ссылка на action/task и фактический outcome); proposed → deferred / expired / superseded / unavailable. «Не сейчас» скрывает предложение и ставит cooldown 30 игровых минут для того же dedup key, но не отменяет потребность/долгосрочное стремление. «Игнорировать» = отсутствие команды; TTL 60 игровых минут по умолчанию, актуальность всегда перепроверяется раньше по изменению фактов; после reconnect не повторять старые неподтверждённые заявки. Не штрафовать послушание, не изменять черты из-за клика. Urgent needs могут предложить новое предупреждение при реальном изменении порога, без спама.
- Один активный bubble; список до 3 актуальных предложений, refresh на значимом событии или не чаще 15 игровых минут для обычного reevaluation в online; критический факт допускает немедленное обновление с dedup. Сроки измеряются игровым временем и не истекают только из-за pause; authority/epoch устаревает в реальном времени независимо. Deferred wish никогда сам не запускается online. При offline новый planner выбирает заново с учётом состояния, а не воспроизводит UI очередь.
- Никакого обязательного квеста, искусственных очков послушания, обязательной «миссии» пресета. Принятие желания — явная команда владельца, тот же arbiter, повторная валидация, если busy/устарело — честный ответ и доступный вариант, без мутации. Пожелания не блокируют прямую команду.
- Utility: hard feasibility filters → критические потребности (offline) → score = bounded need + personality affinity + interest affinity + goal relevance + context/memory − cost/risk/repetition; deterministic tie-break, версия весов/seed. Конкретные коэффициенты принадлежат #401 и проверяемым сценариям, не LLM. Без искусственных расписаний и процентных квот. В online только предложение, не enqueue. Валидатор ограничивает candidate по registry/существующим location/item IDs; интересы без реализованного действия не создают результат. #404 отвечает за творчество/социальные занятия/другие расширения.
- Локальная LLM: опциональный creator draft/biography interpretation, конфликты целей, интерпретация поручений, необычные события и диалоги — только в рамках Tier 1/2 по Конституции. Повседневное планирование и рефлексия о рутинных событиях — deterministic Tier 0. Использовать настроенный локальный транспорт, bounded schemas, timeout/бюджет, без запроса на каждый tick. Для допустимых LLM-запросов планирования default верхнего лимита — 1 запрос на героя за 6 игровых часов; это rate cap, не обязательное расписание вызовов; ограничить очередь и глобальную конкуренцию по существующим settings/budgets. Детерминированный fallback немедленно при недоступности. Worker не удерживает транзакцию во время инференса; свежая транзакция revalidate и fence при ответе, никаких секретов/приватных данных других игроков в prompt. Запись AI decision не есть фактическое исполнение.

## 7. UX и наблюдаемость (#353, #402, #403)
Новый игрок после создания сразу получает управление, без выбора режима. Профиль показывает описание, интересы, вектор, факты биографии; Game Shell — актуальную задачу/место, статус связи и мысли. Bubble над фактическим героем при локальном читаемом маркере, компактный HUD на остальных масштабах и системных экранах. «Согласиться» / «Не сейчас» / самостоятельная команда. Свободный текст (куда пойти/что сделать) интерпретируется в подтверждённую команду, если неоднозначность — уточнение, не выдумывать объект. Нет блокирующей модалки на входе/переходе. Пока offline, engine пишет настоящие события. При следующем join snapshot + cursor interval (последняя утрата presence, текущий snapshot) → краткие 3–5 значимых доступных событий, ссылка в единый журнал; не повторять на каждом heartbeat/reconnect до TTL, нет событий — честно, downtime — не заявлять симуляцию. История не подменяет текущее место/вещи. Статусы и причины локализованы; pending/confirmed/failed/connection lost/expired/busy. Никаких raw mode enums в HUD. Desktop/mobile/focus/reduced motion как #363.

## 8. Миграция, совместимость, последовательность
- До cutover старый main остаётся текущим runtime truth. Сначала additively хранить personality/presence/origin/wish/authority revision и новые контракты; миграция идемпотентна, backup/rollback и data evidence обязательны. Без двойной активации старого и нового scheduler для одного героя. Feature flag для staged release: old path либо new, не оба. Существующие traits, биографии, деньги, inventory, location, history, owner, relations, active/planned tasks и цели сохранять, не mass reset.
- В миграции control_mode не использовать как новый выбор. Все legacy owner characters без активного нового lease = ABSENT; реальный join → PRESENT. Старые DIRECT не застревают. Legacy task source player сохраняется, AI/need/goal без явной player approval — autonomous; неоднозначные source/STARTED rows сверить и нормализовать по фактам, безопасно не активировать неизвестный шаг. Не терять earned effects. Legacy CharacterGoal/Desire сохраняют историю и семантику игрока. Отложенные AI decisions со старой authority invalidated. Не подменять старый /control незаметной фиктивной успешностью.
- Совместимость клиентов: новая server API read model с authority state и task status, без ручного mode; legacy fields временно read-only для совместимости, не публиковать как UX. Зафиксировать API shapes/error codes/idempotency в bounded #398/#399/#400 specs/plan/tasks. Гейт cutover требует совместимой UI, переходов, тестов, rollback plan; код/DB/infra/deploy — только по проектным delivery gates.
- #398 + #399 параллельно после tracked contract gate; #400 после модели #398 (дизайн semantics можно параллельно); #401 после #398/#399/#400. #385/#378/#363/#364 и #402/#403 проектируются по настоящему контракту, не ждать готового backend; реализация этих экранов отдельными bounded issues после handoff. #404 не блокирует MVP. #405 после backend + реальной UI реализации + браузерной приёмки. #365 и #390 — design fixtures, не proof production. #367–#370 — отдельный пилот, не переиспользовать старые режимные ожидания.

## 10. Handoff и открытые вопросы
Контракт определяет политику v1; точные storage/API names, SQL миграция, окончательные score weights, budget измерения и визуальные макеты принадлежат downstream bounded задачам. Прерывание MOVE/TRAVEL_EXTERNAL/CONSTRUCT до завершения — сознательно отложено: текущий engine не предоставляет достаточную промежуточную позицию/универсальный rollback. Удаление ручных режимов не означает расширение каталога занятий. Никакой автоматической симуляции downtime, изменения personality в зрелом возрасте или AI-авторства сообщений игрока в MVP. Для реализации каждой отдельной задачи требуется собственный bounded spec/plan/tasks, scope admission `commit approved` по AGENTS.md и работа через delivery orchestrator. Допуск #397 относится только к документационному контракту, не разрешает production-коммиты, merge или deploy. [План](plan.md) и [очередь](tasks.md) — handoff, не evidence реализации.
